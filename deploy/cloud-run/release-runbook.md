# Cloud Run の公開と切り戻し

手元で確定コミットから Docker イメージを作成し、Artifact Registry に push して Cloud Run を更新する運用を対象とします。秘密値をコマンド履歴・ログ・Issue・PRに記載しないでください。

## 公開前に記録するもの

- プロジェクト、リージョン、サービス、公開URL、現在のトラフィック配分。
- 旧リビジョン、旧イメージのダイジェスト、Secret の参照名とバージョン、CA のマウント設定。
- サービスアカウント、CPU・メモリ、スケーリング、ネットワーク、公開権限、永続ストレージ。
- 公開コミット、検証済みイメージの識別子、実施したテストと未検証事項。

設定の完全な控えが必要な場合はGit管理外のアクセス制限された場所に保存します。環境変数に平文の秘密値が含まれる可能性があるため、サービス定義全体をログに出力しません。Secret の latest 参照を使用している場合は、切り戻し期間中に値を更新せず、旧リビジョンが使用するバージョンを保持します。

## TIDB_* から DB_* への移行

旧リビジョンは旧設定のまま保持します。新しいコードと新しい設定を同じリビジョンに適用し、旧コードだけ、または新設定だけを先に本番へ反映しないでください。

| 新しい変数 | 設定元 |
| --- | --- |
| DB_BACKEND | tidb（TIDB_ENABLE の代替） |
| DB_HOST | 旧 TIDB_HOST |
| DB_PORT | 旧 TIDB_PORT |
| DB_NAME | 旧 TIDB_NAME |
| DB_USER | 旧 TIDB_USER |
| DB_PASSWORD | 旧 TIDB_PASSWORD と同じ Secret を参照 |
| DB_SSL_CA | 旧 TIDB_SSL_CA と同じCAのコンテナ内パス |
| OUTPUT_PDF_DIR | /tmp/exports |

DJANGO_SECRET_KEY、OPENAI_API_KEY、管理者設定、ALLOWED_HOSTS、CSRF_TRUSTED_ORIGINS、DJANGO_DEBUG は維持します。CA の Secret マウントとサービスアカウントも維持します。新リビジョンから旧 TIDB_* 環境変数を除去しても、旧リビジョンの設定は変更されません。既存 Secret 自体は削除・改名しません。

本番設定は稼働サービスから引き継ぎます。検証用の .env.tidb を本番の設定元に使用してはいけません。

## DB とバックアップ

1. 稼働中の旧コードと公開コードのマイグレーション差分を比較します。ブランチ名だけで稼働コードを断定しません。
2. 本番DBへの読み取り確認で、公開コードに未適用のマイグレーションがないか確認します。
3. スキーマ・データ移行がある場合は、旧コードとの互換性を確認し、実行前のバックアップと復元手順を確保します。互換性がない変更はアプリの切り戻しだけで復旧できません。
4. 差分がない場合も、利用可能なバックアップ／復旧手段と対象時点を確認します。再初期化、flush、テスト用DB作成を本番に対して実行しません。

トラフィックなしでデプロイしても、起動時の migrate と管理者初期作成は実行されます。DBへの影響確認はデプロイより前に完了させます。

## 公開の順序

1. develop → main のリリースPRで公開範囲を確認し、公開するタイミングでマージします。
2. main の確定コミットをクリーンに展開してビルドし、コミットを識別できるタグで Artifact Registry に push します。latest だけで公開対象を指定しません。
3. main のマージ結果が検証したソースと一致することを確認します。差分がある場合は再検証し、公開するイメージでも設定テストと静的ファイルの存在を確認します。
4. 旧リビジョンへの100%のトラフィックを維持し、新イメージと新設定をまとめて --no-traffic でデプロイします。イメージはダイジェストで指定し、既存のサービス設定を保持します。環境変数・Secret設定の全置換で既存項目を落とさないようにします。
5. Ready 状態と起動ログを確認します。タグURL等で検証する場合は、必要な ALLOWED_HOSTS／CSRF 設定を事前に設計し、公開する権限範囲も確認します。無条件のホスト許可で対処しません。
6. DB接続・TLS・静的配信を確認してから、新リビジョンへトラフィックを切り替えます。
7. 公開URLで範囲移動、ログイン、単語帳、問題・解答PDF、OCR画面、ログを確認します。更新が必要な確認には検証用データを使います。有料OCRは実施有無を記録します。
8. 成功を確認して公開コミットにリリースタグを付け、コミット・イメージダイジェスト・リビジョン・結果をIssue／PRへ記録します。

## 切り戻し

起動失敗、DB接続失敗、主要機能の退行を認めたら、まず旧リビジョンへ100%のトラフィックを戻します。

```powershell
gcloud run services update-traffic SERVICE --project=PROJECT --region=REGION --to-revisions=OLD_REVISION=100
```

旧リビジョンは旧コード・旧環境変数・Secret参照・CA設定を保持しています。新イメージへ旧変数だけを戻す方法は使用しません。旧リビジョンで起動・ログイン・PDF等が復旧したことを確認し、原因と切り戻し時刻を記録します。

DB変更が適用されていた場合は、事前に確認した互換性・復元手順に従います。バックアップの復元は公開後の更新を失う可能性があるため、影響を評価してから実施します。旧イメージとSecretのバージョンは切り戻し期間中に削除しません。

## deploy ブランチの廃止

公開後確認が完了し、トリガー・スクリプト・ドキュメント・作業環境に旧 deploy ブランチへの有効な参照がないことを確認します。最終コミットを記録し、未移管の変更がなく、旧リビジョンで切り戻せることを確認してからリモートブランチを削除します。

ローカルブランチは未反映変更と他の作業への影響を確認して整理します。/deploy/cloud-run/ ディレクトリは引き続き維持します。
