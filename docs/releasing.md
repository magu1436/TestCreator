# リリース手順

## ブランチとファイルの管理

- `develop`: 未リリースの機能を含む開発ブランチ。
- `main`: 現行リリースを管理するブランチ。
- 作業ブランチは最新の `develop` から作成し、PR の宛先も `develop` とする。
- リリース時は `develop` から `main` へ PR を作成する。

アプリ本体、汎用 Dockerfile、起動処理、環境変数による設定は、両ブランチで共通のファイルを管理します。
Cloud Run 固有の設定・スクリプト・ドキュメントは、必ず [`/deploy/cloud-run/`](../deploy/cloud-run/README.md) に配置します。
以前の `deploy` ブランチは今後の統合先にしません。既存環境の参照先と必要な設定の移管を確認するまでは残します。

## develop 向け PR

1. 最新の `develop` との差分を確認し、必要に応じて変更を取り込む。
2. [本番環境の構築と実行](deployment.md) に従って本番イメージをビルドする。手元の生成済み JS や node_modules がなくても再現できることを確認する。
3. 設定・起動処理のテストを実行し、本番データを含まない検証用 DB で統合テストを行う。
4. 本番構成で各画面を開き、JS/CSS の 404、モジュールの読み込みエラー、コンソールエラーを確認する。
5. ログイン、単語帳表示・編集、範囲指定・移動・折り返し・分割、単語帳切り替え、日本語の問題／解答 PDF を確認する。
6. PR 本文に変更内容、検証対象コミットと実施結果、既知の問題、未検証事項、公開時に必要な設定変更を記載する。確認後に `develop` へマージする。

OCR の実 API 呼び出しは費用が発生するため、実施有無を明記します。実施する場合は、許可された検証用キーと非機密のサンプル画像を使い、抽出結果の表示・修正・保存を確認します。APIキーの値は出力しません。
依存パッケージを変更した場合は、npm audit に加えて、テンプレートの CDN 指定と実際のブラウザ動作も確認します。

作業の進捗メモはリポジトリへコミットせず、Issue／PR のコメントや Obsidian に保存します。正式な運用手順や再利用するテストはリポジトリで管理します。

## main 向けリリース PR と公開

1. `develop` → `main` の PR を作成し、今回公開する変更と関連 Issue を確認する。未公開の別機能が含まれていないかも確認する。
2. 検証結果が公開対象のコードに対応すること、環境変数・証明書・DB接続・永続ストレージ等の実環境設定、公開先の参照コミット／イメージを確認する。
3. 公開のタイミングに合わせて `main` へマージし、対象コミットから作成した検証済みイメージを公開する。マージと本番公開は別操作として扱う。
4. 公開後に起動状態、主要画面、静的配信、PDF生成、ログを確認する。成功後、実際に公開したコミットにリリースタグを付け、関連 Issue の残条件を確認する。

公開前には、直前の正常なリリースのコミット・イメージと実環境設定を記録し、切り戻し方法を確認します。
起動時にマイグレーションが実行されるため、旧イメージへ戻すだけでは DB スキーマは戻りません。DB変更を含むリリースでは、既存データのバックアップと旧アプリとの互換性を別途確認します。
